# Specialist execution and recovery

Use this contract when assigning implementation, review, checking or verification
across engines. A role name or institutional comparison is not evidence of expertise.
The assignment must supply the capabilities an expert needs for this particular job.

For a material delegated assignment, resolve the actual runtime's tools and
permissions, then record the applicable fields below. A one-step read-only consult
needs its question, evidence boundary and answer; do not manufacture a full work packet.

- Outcome and criterion IDs, relevant repository revision, input paths and decisions.
- Domain skills to read from their live source and the rules those skills own.
- Exact write ownership, shared resources, dependencies and publication boundaries.
- Required read, search, execution, browser or source access; confirm each is available.
- Independent checks, evidence locations, remaining budget and a concise return contract.

If a needed capability is absent, route to an available authorised specialist or use
a sequential workflow with explicit `NOT_ASSESSED` evidence. Do not pretend a prompt
grants a tool, credential, sandbox exception or professional qualification. Preserve
the owner's Codex model selection and Claude's separate model policy.

Reviewers inspect the real diff, requirement and test evidence. Give them relevant
fixtures and permission to execute safe checks; default their source edits to read-only.
Keep implementation and acceptance judgements distinct. Findings identify a concrete
failure, location, consequence, reproduction and disposition. Preserve disagreements
until reproduced or resolved with evidence. A vote, score or implementer assurance
does not close an acceptance criterion. Missing specialist evidence stays open.

## Specialist job descriptions

Choose a role when its answer changes a decision. Put the question, evidence and acceptance criterion in the assignment. A brief consultation can be handled by the current agent within its authority. Use the host's delegation rules when assigning a separate worker.

| Role | When to consult | Evidence the specialist returns |
|---|---|---|
| Systems analyst | Workflow ownership, state transitions or exceptions are ambiguous | An actor and decision table, unresolved owner decisions and examples the tester can execute. |
| Accountant | Posting, reversal, valuation or reconciliation rules change | A worked transaction and reversal with expected balances, exceptions and the applicable Accounting Doctrine basis. |
| Auditor | A control requires independent examination | The control objective, sample, records inspected, exceptions and conclusion. Record who implemented the control and who reviewed it. |
| Database administrator | Schema changes, locks, query plans or recovery affect delivery | The affected data and workload, observed plan or lock behaviour, and a migration or restore check appropriate to the change. |
| PHP tester | PHP application behaviour changes | A repeatable test through the application entry point, fixture, PHP version, observed before/after result and remaining coverage gaps. |
| Researcher | A design decision rests on a disputed or changing technical claim | A dated question, primary sources and versions, conflicting evidence, and a conclusion with its limits. |
| Front-end UI/UX specialist | A user journey, interaction or screen changes | The user task, relevant loading/error/success states, rendered narrow and wide views, and observed keyboard and focus behaviour. Apply the project's design and accessibility criteria. |
| Cybersecurity specialist | A change affects authentication, authorisation, data exposure or another trust boundary | A data-flow or control review, affected assets, prioritised findings and defensive regression evidence for applicable controls. |
| Enterprise network specialist (CCNP scope) | Routing, switching, segmentation or failover affects connectivity | A scoped topology, expected traffic paths, observed configuration or telemetry, and verification and rollback criteria. Production changes require existing authority. Record professional credentials only when verified. |

If a connectivity failure could involve either a network path or an access policy, the network specialist establishes where traffic stops and the cybersecurity specialist checks the intended access boundary. Assign independent acceptance where the control requires it.

## Plan-to-run handoff

Keep work admission within the reviewers' capacity. Choose concurrency from
independent ownership, shared-resource contention and the available acceptance
queue, not the number of tasks or agents. A worker reports progress and evidence;
it cannot revise the parent's scope, dependencies or acceptance oracle to obtain
a pass. Return a proposed baseline change with its impact to the plan owner.

Verify both the result and observed execution conduct: required checks ran,
actions stayed in scope and prohibited effects did not occur. Inspect raw
artifacts and the actual diff, including changes to tests and gate configuration;
a summary, role label, schema pass or model vote is insufficient. Stage only
owned paths, then check integration behavior after combining independent work.

The plan owns the intended outcomes; a runner owns execution state. Link stable task
IDs, dependencies, ready conditions, write scopes, acceptance oracles and command
arguments to the project plan in `docs/plans/`. Use a small durable handoff for the
next session: completed criteria and evidence revision, current task, remaining work,
failure signature, next action and external-effect reconciliation requirements.

Continue authorised phases in dependency order without a fresh permission request
at each checkpoint. Retry only when a changed condition or a specific repair makes
the next attempt useful. Keep routine mechanical orchestration outside model calls.
Do not reload whole books, engines, logs or conversation histories into each worker.

## Recovery and progress

Use an authorised, available durable supervisor for long checks. If none is available,
preserve the operation identity and logs and report supervision `NOT_ASSESSED`; a prompt
does not supply the missing service. An observer timeout
does not establish job failure. Reattach to its identity and receipt before starting
another check. After power loss, inspect the saved operation, Git revision, dirty
work and effects; preserve completed work and require explicit replay safety for
interrupted checks. A clean Git tree cannot prove that an external action did not run.

Usage limits produce a persisted waiting state and a bounded next probe, not a model,
account or permission bypass. A provider reset time is known only when supported by
current account evidence. A reboot requires a configured startup mechanism and usable
authentication; detachment alone does not provide it. Preserve explicit stop intent.

Watch output must identify the plan, current action, reported task completion,
independently verified revision, gate progress, retries, wait reason, checkpoint age,
log and next recovery action. Label activity as activity; never invent a percentage,
ETA, token saving or pass. Test both adapter contracts. Exercise each live CLI only
when installed and authorised; otherwise mark that runtime evidence `NOT_ASSESSED`.
Distinguish fake runner tests, live CLI tests, process-death tests and actual reboot evidence.

Durable concepts informing these original procedures: Ediz Najim, *Systems Thinking
for Agentic AI*; Makoto Makino, *Multi-Agent Development with Claude Code*; Jia Huang,
*The Claude Code Operating Model*. Current platform behavior requires Digital Research
verification and tests of the installed version.
